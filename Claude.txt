Paso 3: El arreglo de objetos en datos.js

Este es el corazón del reto. Primero entiende dos conceptos.

Objeto

Agrupa información de una sola cosa con pares clave: valor:

js
const persona = { nombre: "Ana", edad: 30 };

Se accede con punto: persona.nombre.

Arreglo

Una lista ordenada de elementos, entre corchetes. Cada posición tiene un índice que empieza en 0:

js
const frutas = ["manzana", "pera", "uva"];
// frutas[0] es "manzana", frutas[2] es "uva"
Arreglo de objetos

Combina ambos: una lista donde cada elemento es un objeto. Una tabla se representa así: cada fila es un objeto, cada columna es una propiedad.

js
const mascotas = [
  { id: 1, nombre: "Luna", especie: "gato" },
  { id: 2, nombre: "Rocky", especie: "perro" }
];

Tu tarea: convertir las 12 filas de la tabla en 12 objetos, con las propiedades id, fecha, cliente, producto, ciudad, cantidad y precio.

Decisiones de tipos que debes pensar tú:

¿id, cantidad y precio son números o texto? (Pista: ¿vas a querer sumarlos después?)
¿fecha, cliente, producto y ciudad son números o texto? Los textos van entre comillas.
¿Cómo escribirías el precio: 42000 o "42.000"? (Pista: JavaScript no entiende puntos de miles en números.)

Regla de oro del reto: copia los datos tal cual vienen, incluso lo que parezca un error (medellín en minúscula, cantidad 0...). Esos errores son el material del paso 6.

Exportar: module.exports y require

En Node, cada archivo es un módulo aislado. Para usar algo de otro archivo, el archivo que lo tiene debe exportarlo y el que lo necesita debe importarlo:

Al final de datos.js usas module.exports = ... para "publicar" tu arreglo.
En el otro archivo usas require("./ruta") para recibirlo.

Ejemplo de la idea con otro contexto:

js
// matematicas.js
const pi = 3.14159;
module.exports = pi;

// otro.js
const pi = require("./matematicas");

Fíjate en el ./: indica "en esta misma carpeta". Piensa qué ruta necesitarás desde explorar.js.

Cómo verificar: cuenta que tengas 12 objetos y compara cada valor con la tabla. Un error de dedo aquí te complica los pasos siguientes.

Paso 4: src/explorar.js

Este script no modifica nada, solo mira los datos. Debe mostrar cinco cosas:

Qué mostrar	Concepto que necesitas
Cantidad de registros	.length de un arreglo
Primer registro	índice [0]
Último registro	índice [longitud - 1]

Conceptos clave:

.length te da cuántos elementos tiene el arreglo. Si tiene 12, .length es 12, pero el último índice es 11. Eso es lo que te permite calcular el último elemento sin contar a mano.
console.log(...) imprime en la terminal. Úsalo con etiquetas (por ejemplo, un texto que diga qué estás mostrando) para que la salida sea legible.
console.table(...) recibe un arreglo de objetos y lo dibuja como tabla. Pruébalo y compárala con la tabla original.

Ojo con "la posición 4": es el índice 4, lo que en la tabla sería el registro con id 5, porque los índices empiezan en 0. Verifica que tu resultado sea el producto de ese registro. Esta confusión es muy común y es justo lo que el reto quiere que notes.

Working directory: tus archivos tal como están.
Staging (git add): eliges qué cambios entran en la próxima foto.

Guía paso a paso: Minireto 2

Me alegra que el primero haya salido bien. Este reto es el primero de lógica de programación: vas a escribir funciones que recorren los datos y calculan cosas. Lo más valioso de aquí son los tres patrones (contador, acumulador, máximo), porque los vas a usar toda tu carrera.

Antes de programar: los tres patrones

Todos siguen la misma receta: recorres los datos, aplicas una condición y actualizas una variable que arrancó con un valor inicial. Lo único que cambia es qué guardas.

1. Contador: "¿cuántos hay?"

Una variable que arranca en 0 y sube de 1 en 1 cada vez que algo cumple una condición.

js
// ¿Cuántos números son pares?
let pares = 0;
for (const n of [3, 8, 10, 7]) {
  if (n % 2 === 0) {
    pares = pares + 1;
  }
}
// pares vale 2
2. Acumulador: "¿cuánto suman?"

Una variable que arranca en 0 y le vas sumando algo en cada vuelta.

js
let suma = 0;
for (const n of [3, 8, 10, 7]) {
  suma = suma + n;
}
// suma vale 28
3. Máximo: "¿cuál es el mayor?"

Guardas el mejor candidato hasta ahora y lo reemplazas cuando aparece uno mejor. Aquí está la parte delicada: ¿con qué valor inicias?

js
let mayor = null;            // todavía no hay candidato
for (const n of [3, 8, 10, 7]) {
  if (mayor === null || n > mayor) {
    mayor = n;
  }
}

Fíjate en la condición doble: si todavía no hay candidato (null), el primer elemento se convierte en candidato automáticamente. Si iniciaras mayor en 0, funcionaría con números positivos pero fallaría con negativos. Y si iniciaras en 0 para guardar un registro completo (objeto), no tendría sentido. Por eso null es la inicialización honesta: "aún no hay ninguno".

El ciclo for...of

Recorre un arreglo elemento por elemento, sin que manejes índices:

js
for (const venta of ventas) {
  // aquí "venta" es un elemento distinto en cada vuelta
}

Se lee: "para cada venta dentro de ventas". Usas const porque dentro de cada vuelta la variable no se reasigna.

Paso 1: Pseudocódigo en la bitácora (hazlo primero)

El pseudocódigo es escribir el algoritmo en español, con pasos claros, sin sintaxis de JavaScript. Su propósito es que pienses la lógica antes de pelear con comas y llaves.

Para cada indicador, tu plan debe responder las cuatro preguntas que te dan:

¿Qué recorro?
¿Qué condición aplico? (puede ser "ninguna")
¿Qué acumulo o cuento?
¿Con qué valor inicio?

Ejemplo de formato, con un indicador que no es de tu reto (cuántas ventas hay de Cali):

Indicador: contar ventas de Cali
- Inicio: contador = 0
- Recorro: cada venta del arreglo
- Condición: si la ciudad de la venta es "Cali"
- Acción: sumo 1 al contador
- Al terminar: devuelvo el contador

Debes hacer uno así para cada indicador: valorVenta, totalVendido, unidadesVendidas, ventaMayor, ticketPromedio y ventasPorCiudad. En ventaMayor y ticketPromedio piensa especialmente en qué pasa si el arreglo viene vacío; lo vemos en el paso 6.

Paso 2: valorVenta(venta)

Una función es un bloque con nombre que recibe datos (parámetros), hace algo y devuelve un resultado con return:

js
function areaRectangulo(base, altura) {
  return base * altura;
}
areaRectangulo(3, 4); // 12

Tu función recibe un objeto venta (no el arreglo) y devuelve el producto de dos de sus propiedades. Recuerda cómo se accede a una propiedad: venta.cantidad.

Por qué es la base de todo: si mañana el negocio cambia la fórmula del valor (por ejemplo, agrega un descuento), la cambias en un solo lugar y todas las demás funciones se actualizan. Eso se llama no repetir código.

Paso 3: totalVendido, unidadesVendidas y ventaMayor

Los tres reciben el arreglo completo como parámetro y usan for...of.

totalVendido(ventas): patrón acumulador. Cada vuelta suma el valor de una venta. No calcules cantidad * precio aquí; llama a valorVenta, como pide el reto. Llamar una función es escribir su nombre con el dato entre paréntesis.

unidadesVendidas(ventas): también acumulador, pero acumulas otra cosa. Piensa: ¿qué propiedad sumas ahora?

ventaMayor(ventas): patrón máximo. Dos detalles clave:

Compara valores (usa valorVenta para ambos lados de la comparación), pero guarda el registro completo, no el número. Necesitas, por tanto, una variable para el candidato (null al inicio).
Si el arreglo está vacío, el ciclo no da ninguna vuelta y devuelves lo que tenía el candidato inicial. Ya tienes parte de la respuesta del paso 6.
Paso 4: ticketPromedio(ventas)

El ticket promedio es: total ÷ cantidad de ventas. Aquí usas dos patrones a la vez en el mismo ciclo: acumulador (para el total) y contador (para cuántas ventas).

El reto añade una condición: solo cuentan las ventas válidas (cantidad > 0). Esto conecta directo con el caso borde de la venta 8 que ya detectaste en el reto anterior. Piensa:

¿La condición if (venta.cantidad > 0) envuelve solo el contador, solo el acumulador o ambos? (Pista: si la venta 8 vale 0 × 42000 = 0, ¿cambia el total si la incluyes? ¿Y el contador?) Entender por qué importa el contador es el punto del ejercicio.
Peligro: división entre cero. Si no hay ventas válidas, total / 0 en JavaScript da Infinity o NaN, no un error. El criterio de aceptación dice que no puede devolver NaN. Necesitas una condición antes de dividir.
Paso 5: ventasPorCiudad(ventas, ciudad)

Esta función recibe dos parámetros: el arreglo y el texto de la ciudad que buscas. Es un acumulador con condición.

El reto central es normalizar: convertir los textos a una forma estándar antes de compararlos. Dos métodos de texto lo resuelven:

.trim() quita espacios al inicio y al final: "  Cali ".trim() → "Cali"
.toLowerCase() pasa todo a minúsculas: "CALI".toLowerCase() → "cali"

Se pueden encadenar: texto.trim().toLowerCase().

La idea: normaliza ambos lados de la comparación, la ciudad de la venta y la ciudad que te pasan como parámetro. Si solo normalizas uno, buscar "Medellín" no coincidirá con "medellín ".

Ojo con el caso exacto que te piden verificar: la venta 5 tiene la ciudad escrita distinto a las demás ventas de Medellín. Tu función debe incluirla.

Esta es la solución real al caso borde de las ciudades que documentaste: no modificas los datos originales, normalizas al momento de comparar.

A que se refiere con ticketPromedio?

Un ticket promedio es cuánto gasta, en promedio, un cliente cada vez que compra. Es un término muy usado en comercio: cada venta (cada "ticket" o recibo) tiene un valor, y el ticket promedio es el valor típico de una compra.

La fórmula

ticket promedio = valor total vendido ÷ número de ventas

Ejemplo con otro negocio (una panadería con 3 ventas del día):

Venta	Valor
1	10.000
2	20.000
3	30.000
Total vendido: 60.000
Número de ventas: 3
Ticket promedio: 60.000 ÷ 3 = 20.000

Se lee: "en promedio, cada compra fue de 20.000".

Por qué le sirve a la gerente: responde "¿cuánto gasta un cliente por compra?". Si el ticket promedio sube, los clientes están comprando más (o productos más caros) en cada visita.

Ojo con lo que NO es:

No es el total vendido (eso es la suma de todo).
No es lo que gasta un cliente en total a lo largo del tiempo. Es por compra, no por cliente. Fíjate que C01 aparece en tres ventas; cada una cuenta como una compra distinta.

El factor depende de la complejidad en tiempo de cada funcion, no de la funcion en si. Se calcula asi:

factor = (nuevo n ÷ n medido) elevado a la potencia de la complejidad

De 10.000 a 1.000.000 ventas, n se multiplica por 100. Entonces:

Complejidad	Que se hace	Factor
O(1)	100 elevado a 0	1 (no cambia)
O(n)	100 elevado a 1	100
O(n²)	100 elevado a 2	10.000
Factor de cada funcion
Funcion	Tiempo	Factor
valorVenta	O(1)	1
primeraVenta	O(1)	1
totalVendido, unidadesVendidas	O(n)	100
ventaMayor, ticketPromedio, ventasPorCiudad	O(n)	100
totalVendidoM, unidadesVendidasM, ventasPorCiudadM	O(n)	100
totalPorCiudad, unidadesPorProducto	O(n)	100
ventasDelDia	O(n)	100
totalCiudadCadena, totalCiudadUnaPasada	O(n)	100
topProductosPorValor	O(n + p log p)	100 (ver nota)
clientesRecurrentes	O(n²)	10.000
Aclaraciones para el informe

topProductosPorValor: su tiempo tiene dos partes. El recorrido de las ventas crece con n (factor 100), pero el sort depende de p, los productos distintos, que en tu generador siempre son 5. Como p no crece con n, el sort no se multiplica, y el factor practico es 100. Escribe esa explicacion en una nota.

Las versiones con 4 recorridos (totalCiudadCadena) usan el mismo factor 100 que las de un recorrido, por lo que ya viste: las constantes no cambian como crece la funcion. Su tiempo sera mayor, pero se multiplica igual.

clientesRecurrentes: el factor 10.000 supone el comportamiento tipico. Menciona que, por el costo oculto de includes, el peor caso podria ser peor.

Como se usa
tiempo proyectado a 1.000.000 = tiempo medido a 10.000 × factor

Ejemplo con un numero inventado: si clientesRecurrentes tardara 100 ms con 10.000 ventas, con 1.000.000 tardaria 100 × 10.000 = 1.000.000 ms, que son 1.000 segundos, unos 17 minutos. Cambia ese numero por el tuyo.

Dos precauciones
Funciones de menos de 1 ms: multiplicar "menos de 1 ms" por 100 da un numero poco confiable. Para esas, repite la funcion muchas veces al medir y divide, o mide directamente con 1.000.000 de ventas, que en una funcion lineal es rapido. Si lo haces, anota que ese dato es medido y no proyectado.
Es una estimacion: deja escrito en la seccion que el factor supone que la funcion sigue creciendo igual, y que a tamanos grandes pueden influir la memoria disponible y otros efectos.
